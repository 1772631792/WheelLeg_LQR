# 从仿真到实物：可移植控制核心与“生产代码导出”方案

## 1. 结论

这个想法可行，而且比直接移植 `balance_chassis-main` 更适合作为以后新嵌入式工程的基础。

建议实现的不是一个完整的 Simulink 克隆，而是一个范围清晰的“控制生产代码系统”：

1. 在 PC 上完成建模、增益计算、参数检查和仿真验证；
2. 在线控制算法只使用可预测、无平台依赖的 C99/C11；
3. 同一份在线 C 源码同时编译为桌面仿真库和 MCU 目标代码；
4. 导出工具把算法源码、生成参数、公开头文件、版本清单和测试向量复制到一个自包含文件夹；
5. 新嵌入式工程只需要实现一层很薄的传感器/电机适配，不需要复制 RTOS、HAL、CAN、日志、UI 等旧工程模块。

这可以实现 Simulink Coder 最有价值的部分：**模型/参数在 PC 侧生成，固定周期的生产代码在嵌入式侧执行，并且仿真与实物使用同一算法核心**。完整实现 Simulink 的图形建模器、任意模块调度、类型推导和通用代码生成器则成本非常高，目前没有必要。

当前 UI 的“生产代码导出”已经采用更接近 Simulink Coder 的公开形式：`wheel_leg_U`、`wheel_leg_Y`、`wheel_leg_B`、`wheel_leg_DW`、`wheel_leg_P`，以及 `wheel_leg_initialize()`、`wheel_leg_step()`、`wheel_leg_terminate()`。自定义控制放在 `wheel_leg_user.c`；PID 通过 `void *` 实例与 `calculate/reset` 函数接口绑定，因此应用可以原样使用自己的 `PIDInstance` 和完整 PID 功能。重复导出时用户文件会保留，不会覆盖用户控制代码。

## 2. 当前工程已经具备的基础

当前链路已经完成了一次重要验证：

```text
MuJoCo 物理模型
      │ 传感器状态
      ▼
simulation/firmware_native.py
      │ 固定数组 ABI
      ▼
controller/firmware_bridge.c
      │ 调用原五连杆、VMC、LQR/MPC 算法
      ▼
六个电机力矩
```

`firmware_bridge.c` 中的 `FW_Reset()`、`FW_Update()` 已经很接近生产代码入口；在线控制部分也使用固定数组、静态状态和 `float`，没有把 Python 或 MuJoCo 放进控制决策。

但它还不是最终的可移植产品，原因包括：

- 直接包含 `balance_chassis-main` 内部头文件，数据结构仍带有原工程语义；
- 依赖 `firmware_compat` 模拟 `arm_math.h`、`super_cap.h` 等环境；
- 控制参数、状态机、几何参数和平台桥接仍混在一个文件中；
- 使用全局静态状态，接口不能自然支持多个实例；
- 缺少正式的版本、参数 CRC、执行时间预算和嵌入式在环测试合同；
- 当前仿真传感器较理想，未完整覆盖编码器量化、延迟、IMU 滤波、丢包和实物力矩标定。

所以，当前桥接层应当作为“算法等价性原型”，下一阶段再整理成独立生产包。

## 3. 最终希望得到什么

每次导出形成一个可直接复制的目录，例如：

```text
wheelleg_control_export/
├─ include/
│  ├─ wlc_api.h              # 唯一主要外部接口
│  ├─ wlc_types.h            # 固定宽度类型、输入输出结构
│  └─ wlc_config.h           # 编译期能力开关
├─ src/
│  ├─ wlc_core.c             # Init/Reset/Step、模式和调度
│  ├─ wlc_kinematics.c       # 五连杆与 Jacobian/VMC
│  ├─ wlc_lqr.c              # 增益调度和状态反馈
│  ├─ wlc_pid.c              # 小型、无堆分配 PID
│  ├─ wlc_safety.c           # 限幅、故障、斜坡和降级
│  └─ wlc_math.c             # 极少量可替换数学函数
├─ generated/
│  ├─ wlc_params.c           # 几何、质量、限幅和控制参数
│  ├─ wlc_params.h
│  ├─ wlc_gains.c            # PC 离线生成的 LQR/MPC 系数
│  └─ wlc_gains.h
├─ examples/
│  ├─ baremetal_adapter.c    # 裸机定时器调用示例
│  └─ freertos_adapter.c     # RTOS 任务调用示例
├─ tests/
│  ├─ golden_input.csv       # 桌面仿真记录的输入
│  ├─ golden_output.csv      # 对应期望输出
│  └─ test_runner.c
├─ CMakeLists.txt
├─ manifest.json             # 版本、单位、周期、参数 CRC、生成时间
├─ LICENSES/
└─ README.md
```

这个目录应满足以下约束：

- 只依赖 ISO C 标准头和可选的 `libm`；
- 不包含 STM32 HAL、FreeRTOS、CAN、电机驱动、Python 或 MuJoCo 头文件；
- 不进行 `malloc/free`，不使用递归和可变长度数组；
- 所有循环上界在编译期确定；
- 默认使用 `float`，离线设计和测试可使用 `double`；
- 用 GCC、Clang、arm-none-eabi-gcc 均能独立编译；
- 将该文件夹复制进一个空工程后，不需要回到原仓库寻找隐藏依赖；
- 导出包的测试程序可以在 PC 上复现相同输入输出。

“只复制一个文件夹”是导出结果，不代表所有代码必须塞进一个 `.c` 文件。保持 5～8 个职责明确的小文件通常比单个巨型文件更容易审查、裁剪和移植；如果确有需要，导出器还可以额外生成 amalgamation 版本 `wlc_all.c + wlc_all.h`。

## 4. 推荐的公共接口

不要让算法层直接读取全局 IMU、电机对象或 CAN 数据。算法只接收数值输入并返回数值输出：

```c
typedef struct {
    float pitch_rad;
    float pitch_rate_rad_s;
    float roll_rad;
    float roll_rate_rad_s;
    float yaw_rad;
    float yaw_rate_rad_s;
    float distance_m;
    float velocity_m_s;
    float joint_angle_rad[4];
    float joint_rate_rad_s[4];
    float normal_force_n[2];
    uint32_t valid_flags;
} WlcInput;

typedef struct {
    float velocity_m_s;
    float yaw_rate_rad_s;
    float leg_length_m;
    uint32_t mode_flags;
} WlcCommand;

typedef struct {
    float wheel_torque_nm[2];
    float joint_torque_nm[4];
    uint32_t status_flags;
} WlcOutput;

typedef struct WlcContext WlcContext;

int  Wlc_Init(WlcContext *ctx, const WlcConfig *config);
void Wlc_Reset(WlcContext *ctx, const WlcInput *initial);
int  Wlc_Step(WlcContext *ctx,
              const WlcInput *input,
              const WlcCommand *command,
              WlcOutput *output,
              WlcDiagnostics *diagnostics);
```

关键规则：

- `Wlc_Step()` 每个固定控制周期只调用一次，例如严格 1 kHz；
- 接口字段明确写出单位，内部统一使用 SI；
- 坐标正方向、左右腿顺序、电机正方向写入接口文档和自动测试；
- 算法状态全部放入调用者分配的 `WlcContext`，不依赖隐藏全局变量；
- `WlcContext` 可以是不透明结构，也可以提供 `WLC_CONTEXT_SIZE` 供静态分配；
- 返回值表示调用是否有效，详细降级原因通过 `status_flags` 输出；
- 输出在任何错误路径下都必须确定，通常为受控斜坡降力或零力，不能保留上一次随机值。

嵌入式工程的硬件适配只做三件事：

```text
编码器、IMU、CAN反馈 ──标定/换算──> WlcInput
遥控器、上层命令     ──限幅/模式──> WlcCommand
WlcOutput            ──力矩到电流──> 各电机驱动
```

算法核心不应知道使用的是 STM32、TI、ESP32、裸机还是 FreeRTOS。

## 5. 四层架构

### 5.1 离线设计层（PC）

负责：

- 根据质量、惯量、腿长节点和控制周期建立模型；
- 离散化并求 LQR/有限步 MPC 参数；
- 对腿长节点进行拟合或查表；
- 做闭环特征值、可控性、参数范围和数值条件检查；
- 输出 `wlc_gains.c/h`、`wlc_params.c/h` 和参数清单。

这一层可以使用 Python、NumPy、SciPy，甚至 MATLAB，但它们都不进入 MCU。当前 `simulation/source_design.py` 和 `controller/riccati6.c` 已经属于这一层的雏形。

嵌入式侧通常不需要在线求 Riccati 方程。在线只需要用 Horner 形式计算三次多项式增益：

```c
k = ((a * leg_length + b) * leg_length + c) * leg_length + d;
```

这样速度快、内存固定，也更容易做最坏执行时间分析。

### 5.2 在线控制核心（Portable Core）

只负责确定性的单步计算：

- 输入合法性检查；
- 五连杆正运动学、速度和 VMC；
- 状态估计中适合放入核心的确定性部分；
- LQR/MPC 增益调度；
- 腿长、横滚、航向控制；
- 离地、越阶和零力等状态机；
- 扭矩饱和、抗积分饱和和安全降级；
- 输出诊断数据。

它是 MuJoCo、SIL 测试、PIL 测试和实车共同使用的唯一算法实现。

### 5.3 平台适配层（不导入核心）

每个嵌入式工程自己实现：

- 定时器/RTOS 周期调度；
- IMU、编码器、CAN 和电机驱动；
- 电机零位、减速比、方向和力矩常数标定；
- 通信看门狗和板级急停；
- 参数在 Flash 中的读取、升级和回滚；
- 日志上传和调试接口。

适配层可以依赖 HAL、FreeRTOS 或厂商 SDK，但这些依赖不能反向渗入在线控制核心。

### 5.4 导出与验证层

建议最终提供一个命令：

```powershell
python tools/export_control.py --profile config/robot_A.json --out dist/wheelleg_control
```

它应执行：

1. 校验模型参数和控制周期；
2. 重新生成增益及参数源文件；
3. 运行单元测试、SIL 和仿真回归；
4. 从明确的白名单复制核心文件，而不是递归复制整个仓库；
5. 在临时空目录中只用导出包自身执行一次编译；
6. 扫描禁止依赖，例如 `HAL_`、`FreeRTOS`、`pvPortMalloc`、`malloc`；
7. 生成 `manifest.json`、参数 CRC、版本号和测试摘要；
8. 可选交叉编译并报告 Flash、RAM、栈和最坏执行时间。

只有全部步骤通过，才产生“可用于集成”的导出包。这就是类似 Simulink 的生产代码功能，而不是简单复制几个当前看起来能编译的文件。

## 6. 从仿真打通到实物的验证阶梯

不要从 MuJoCo 通过后直接上完整功率实车。建议按以下阶梯推进：

### 阶段 A：明确控制合同

- 冻结 `WlcInput/WlcCommand/WlcOutput`；
- 写清坐标、单位、周期、时间戳和符号；
- 明确每个传感器的有效范围与无效行为；
- 明确轮电机、四个关节电机的顺序和正方向；
- 将仿真中的理想量对应到实车可测量量。

特别要解决：当前 MuJoCo 直接给出接触法向力，实车不能天然获得这个量。必须确定由关节力矩、IMU、腿加速度、弹簧/力传感器或其他观测器得到离地状态，不能把仿真真值直接搬到实车。

### 阶段 B：SIL（Software-in-the-Loop）

- MuJoCo 继续调用生产核心；
- 保存每个 1 ms 输入、内部状态和输出；
- 针对站立、加速、急停、转向、伸缩腿、台阶、腾空和传感器异常形成黄金数据；
- PC GCC、Clang 和不同优化等级输出应在约定误差内一致；
- 对 NaN、丢包、越界角度、控制周期抖动做故障注入。

### 阶段 C：PIL（Processor-in-the-Loop）

- 将相同核心编译到目标 MCU；
- PC 通过 UART/CAN/USB 每 1 ms 发送记录输入；
- MCU 执行 `Wlc_Step()` 并回传输出；
- 与 PC 黄金输出逐样本比较；
- 测量周期、最坏执行时间、栈峰值和数值差异。

建议控制计算最坏时间不超过周期的 30%～50%，为中断、通信和保护留出余量。1 kHz 控制应避免在热路径中做大矩阵求逆、动态内存和无界迭代。

### 阶段 D：HIL（Hardware-in-the-Loop）

- MCU 运行真实生产核心和真实调度；
- MuJoCo 或实时仿真器提供虚拟 IMU/编码器；
- MCU 输出电机力矩命令返回仿真；
- 注入 CAN 延时、丢帧、编码器量化、传感器噪声和偏置；
- 验证看门狗、零力、限幅和状态机。

Windows 普通进程不保证严格 1 kHz 实时，因此初期可用于功能 HIL；若要验证严格时序，需要实时 Linux、专用实时机或至少使用 MCU 定时器作为主时钟。

### 阶段 E：低风险实物调试

推荐顺序：

1. 电机拆载，确认 CAN ID、反馈频率和电流/力矩方向；
2. 单关节小电流，确认零位、角度范围、减速比和扭矩常数；
3. 单腿悬空，验证五连杆角度、腿长、Jacobian 和 VMC 方向；
4. 机体吊架保护，轮子离地，验证姿态反馈符号；
5. 低腿、低扭矩、限位绳/保护架下站立；
6. 小速度直行，再做转向和变腿长；
7. 最后才做台阶、跳跃和高功率动作。

每一步都要有物理急停、通信看门狗、姿态阈值、关节软硬限位、力矩变化率限制和掉线归零。仿真稳定不等于实物安全。

## 7. 实物前必须补齐的模型与标定

当前仿真适合验证控制结构，但要实现可信的 sim-to-real，还需测量或辨识：

| 项目 | 当前情况 | 实物要求 |
|---|---|---|
| 机身/杆件/轮质量与惯量 | 部分取参考值，部分是假设 | 称重、CAD 或摆实验辨识 |
| 电机力矩 | 仿真直接施加 Nm | 标定电流到输出轴力矩、减速比、效率和摩擦 |
| 电机/通信延迟 | 基本理想 | 测量 CAN 周期、驱动延迟、反馈延迟和丢包 |
| IMU | 理想姿态和角速度 | 零偏、安装旋转、滤波延迟、温漂和振动 |
| 编码器 | 理想连续角度 | 零位、方向、跨圈、量化和安装误差 |
| 轮胎接触 | MuJoCo 参数 | 摩擦、轮胎变形、侧滑和地面差异 |
| 法向力/离地 | 直接读取接触力 | 设计可部署的观测器或真实传感器 |
| 结构限位 | 已有仿真关节限位 | 对应真实硬限位、软限位和线缆空间 |
| 电源 | 未完整模拟 | 电压跌落、峰值电流、超级电容和功率限制 |

推荐在仿真中加入这些误差的可配置模型，并用参数随机化做批量测试。目标不是让单次理想仿真更漂亮，而是让控制器在一组合理的不确定性中仍然安全、可恢复。

## 8. 高效和易移植的具体规则

### 在线算法规则

- 固定周期、固定尺寸、固定内存；
- 所有参数在初始化时校验，周期函数不做文件读取；
- 小矩阵手写展开或使用固定尺寸函数，不引入通用动态矩阵框架；
- 增益离线生成，在线查表、线性插值或 Horner 求值；
- 三角函数集中在运动学层，能复用中间量就不重复计算；
- 避免 `powf(x, 2)`，使用 `x*x`；
- 对接近奇异位形显式检测，不能继续除以很小的 `sin()`；
- 所有积分器有抗饱和、复位和模式切换策略；
- 力矩除了幅值限位，还要有变化率限制；
- 发布版本开启有限值检查和关键范围检查，不能只在调试版保护；
- 不使用未定义行为，不依赖编译器特有的结构体布局。

### 依赖策略

核心默认只使用：

```text
stdint.h, stddef.h, math.h, string.h
```

若目标平台需要更快的 `sin/cos/sqrt`，通过 `wlc_math.h` 的少量函数替换，不让 CMSIS-DSP 类型进入算法接口。例如：

```c
#ifndef WLC_SIN_F
#define WLC_SIN_F sinf
#endif
```

这样默认版本无需 CMSIS；STM32 工程可在编译配置中选择 CMSIS 或硬件加速实现。

### 数值策略

- 生产运行使用 `float32`；
- 离线设计和参考测试使用 `float64`；
- 黄金测试允许基于绝对误差和相对误差的容差；
- 编译时明确是否允许 `-ffast-math`，初期不要默认开启；
- 记录每个目标编译器和优化等级的回归结果；
- 对 FPU 缺失的平台单独评估，不要假设同样的 1 kHz 性能。

## 9. 参数与代码的边界

应该生成或配置的数据：

- 质量、惯量、轮径、轮距和连杆长度；
- 控制周期；
- LQR/MPC 系数；
- PID 参数；
- 电机力矩、腿长、角度和速度限制；
- 状态机阈值和超时时间；
- 传感器有效范围。

应该保持为稳定代码的部分：

- 五连杆运动学公式；
- LQR 状态误差与增益调度流程；
- PID、饱和与抗饱和实现；
- 状态机框架；
- 故障与降级规则；
- API 和诊断结构。

每次参数生成都应携带：

- 参数 schema 版本；
- 算法代码版本或 Git commit；
- 控制周期；
- 浮点格式；
- 参数 CRC；
- 生成器版本；
- 验证用例及结果摘要。

实物启动时可以把固件内置 CRC 上报给上位机，防止“仿真使用 A 参数、实车烧录 B 参数”却难以追踪。

## 10. 与完整 Simulink 功能的边界

### 值得实现

- 参数文件到 `.c/.h` 的确定性生成；
- 固定控制模块的组合和固定周期调度；
- 自动导出自包含源码包；
- SIL/PIL 黄金向量验证；
- 依赖、内存、执行时间和代码规范检查；
- 版本、CRC 和可追溯报告；
- 少量经过验证的模块模板，例如 PID、状态空间、查表、限幅、滤波和状态机。

### 暂时不值得实现

- 通用图形化拖拽编辑器；
- 任意采样率自动调度与代数环求解；
- 通用符号推导和任意模型代码生成；
- 覆盖 Simulink 全部 block；
- 自动生成所有 MCU 外设驱动；
- 没有边界的第三方库兼容层。

如果未来确实需要图形模型，可以先定义一个很小的声明式模型格式，只允许经过验证的固定模块，再生成调用顺序和参数。不要一开始追求通用 Simulink，否则大量精力会花在编辑器、调度器和边角语义上，而不是控制器正确性。

## 11. 推荐实施路线

### 第 0 阶段：冻结基线

- 保存当前 MuJoCo 场景的黄金输入输出；
- 记录当前增益、参数、编译器和测试结果；
- 明确哪些行为必须逐样本等价，哪些允许改进；
- 将原工程 MIT 许可和修改说明纳入导出许可清单。

验收：任意后续重构都能自动判断是否改变控制行为。

### 第 1 阶段：定义 API 和数据合同

- 定义 `WlcInput/WlcCommand/WlcOutput/WlcDiagnostics/WlcContext`；
- 冻结单位、坐标、符号和调用周期；
- 给每个字段写范围、失效行为和来源。

验收：MuJoCo 和一个空白 MCU 示例都只依赖同一个 `wlc_api.h`。

### 第 2 阶段：提取自包含核心

- 从 `firmware_bridge.c` 与原工程中提取必要数学逻辑；
- 用自己的最小数据结构替代 `balance.h` 的工程级结构；
- 移除 `arm_math.h`、`super_cap.h`、HAL、RTOS 和电机对象依赖；
- 将隐藏静态状态放入 `WlcContext`；
- 保留原始算法的许可证和来源标注。

验收：核心在一个空目录中只凭自身文件通过 GCC/Clang 编译，并与基线输出一致。

### 第 3 阶段：参数生成

- 将几何、质量、限制和增益统一放入 schema；
- 生成只读 `const` 参数源文件；
- 添加参数范围、单位和 CRC；
- 把离线 Riccati、拟合和稳定性检查接入生成流程。

验收：同一份参数描述同时驱动 MuJoCo 配置和生产控制参数，禁止人工复制两份数字。

### 第 4 阶段：生产安全层

- 输入有效位和时间戳检查；
- 传感器超时、关节越界、姿态过大、数学奇异和 NaN 处理；
- 力矩幅值/变化率限制、积分器复位和模式无扰切换；
- 明确定义正常、降级、零力、锁止和恢复状态。

验收：故障注入时输出始终有限、可预测，并在规定时间内进入安全状态。

### 第 5 阶段：自动导出

- 实现白名单复制和参数生成；
- 生成清单、许可证、示例和测试数据；
- 在隔离目录独立编译；
- 输出依赖、ROM/RAM 和测试报告；
- 可选生成单文件版本。

验收：把导出目录复制到另一台机器的空 C 工程即可编译测试，无需原仓库。

### 第 6 阶段：PIL/HIL

- 制作串口/CAN 输入输出回放协议；
- 在目标 MCU 上比较黄金向量；
- 测量最坏执行时间和栈；
- 用仿真注入噪声、延迟和故障。

验收：目标 MCU 与 PC 参考输出在容差内一致，且满足实时和资源预算。

### 第 7 阶段：实物渐进联调

- 完成传感器、电机、结构和电源标定；
- 按单电机、单腿、吊架、低功率站立、低速运动逐步开放；
- 每一步都保存实车日志并回灌仿真；
- 用实测数据更新模型，而不是只在实车上不断调 PID。

验收：规定工况下的稳定性、温度、电流、时序、保护和恢复均达到测试标准。

## 12. 下一步最合适做什么

暂时不改算法的前提下，下一步建议先完成两项设计工作：

1. **写正式 I/O 合同**：逐项确定实车能提供什么传感器量、频率、延迟、单位、方向和失效标志；尤其确定法向力/离地状态在实车上的来源。
2. **建立黄金回放数据**：从当前 MuJoCo 保存多个工况的 1 kHz 输入、输出和关键内部量，作为以后提取可移植核心时的等价性标准。

之后再提取 `portable_control`。先有接口和黄金数据，再拆代码，可以避免“看起来移植成功，但状态符号、滤波、积分器或时序已经悄悄改变”。

长期目标可以概括为：

```text
模型与参数（PC）
      │ 自动生成
      ▼
自包含 portable_control
   ┌──┴───────────┐
   ▼              ▼
MuJoCo/SIL      MCU/PIL/实车
   └────黄金数据对比────┘
```

这条路线既保留了类似 Simulink 的可追溯生产代码能力，也避免把庞大的工具链和工程依赖带进嵌入式项目。
